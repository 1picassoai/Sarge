# Paying for the rules once

**Sun 13 September 2026.** The rules that pass VET are identical on every call. Today
they are re-tokenised and re-attended on every turn, because a system message is only
text at the front of a prompt. This POC computes them once and keeps the result.

---

## Why it is possible at all

Attention is causal. Token 7 attends to tokens 1–6 and never to 8, so token 7's keys and
values **cannot change** once computed. That is the whole reason a KV cache exists — and
the reason a prefix's cache can be computed once, written to disk, and loaded into a
fresh context later.

llama.cpp exposes exactly that: `state_save_file` and `state_load_file`.

---

## What was run

```
kv --build                              prefill the INJECT rules, save the state
kv --task "add a delete customer endpoint"          load it, then answer
kv --task "add a delete customer endpoint" --cold   same task, no state
```

```
built      6 rule(s), 164 tokens, prefilled in 152 ms
saved      harness/vetted.kv  (23.1 MB)

WARM       17 of 181 tokens prefilled in 86 ms  (state loaded in 18 ms)
COLD       181 of 181 tokens prefilled in 151 ms
```

**The warm run prefilled 17 tokens instead of 181.** The other 164 were already in the
cache.

---

## The check that matters

Both runs produced **byte-identical output**, down to the markdown:

```csharp
app.MapDelete("/customers/{id}", async (int id, ApplicationDbContext dbContext) =>
{
    var customer = await dbContext.Customers
        .FirstOrDefaultAsync(c => c.Id == id);
    if (customer == null)
    {
        return Results.NotFound();
    }
    customer.IsArchived = true;
    await dbContext.SaveChangesAsync();
```

A loaded state that changed the answer would make every timing number meaningless. It
did not. The rules held: archived, not deleted, and minimal API rather than a controller.

---

## What the numbers are not

**151 ms → 86 ms is real, and it is small.** 164 rule tokens is a short prefix and a
4070 prefills quickly. Anyone reading this as "43% faster" has read it wrong — that is
one measurement on one prompt, and most of the wall clock is generation, which this does
not touch at all.

**What the POC proves is the mechanism, not the saving.** The cost of the rules changes
from O(whole prompt) every turn to O(new tokens) every turn. Where that pays:

- a rulebook of fifty rules instead of six
- an agent loop making many short calls against the same rules
- a slower device, where prefill dominates
- a long-lived session, where the same prefix is paid for again and again

**The state file is 23 MB for 164 tokens**, because llama.cpp writes the whole context
allocation rather than only the occupied part. It is gitignored and regenerated by
`--build`.

---

## The delta

The saved state records the exact token sequence it was built from. On load, that is
compared against the current VETTED.md:

```
warning    the saved state does not match the current VETTED.md
           re-run --build; the rules have changed since it was saved
```

Silently serving a stale cache would mean the model is grounded in rules that no longer
exist — the exact pollution VET is there to prevent, arriving by the back door.

---

## What is still not done

This is a **prefix cache**, not injection into a running context. The rules are loaded
before the conversation starts rather than woven into an existing one, and the state is
per-model and per-context-size — change either and it must be rebuilt.

It is also not yet part of `compile`. The two binaries share `vetted.rs` but `compile`
still puts the rules in a system message. Merging them is the next step, once this
mechanism has been beaten on a bit harder.
